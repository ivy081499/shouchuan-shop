# ADR-0012 自建前台，FreeStore 轉為過渡並行

**狀態**：已採用（**取代 ADR-0008 的前台部分**）
**日期**：2026-09-22

## 背景

ADR-0008（2026-09-11）決定前台用 FreeStore、本系統只做後台。當時的判斷是：
店主零客戶，最該驗證的是「有沒有人買」，而不是「系統好不好」。

兩週後店主提出兩件事：

1. **後台上架功能殘缺，無法完整管理商品**
2. **前台原本打算用別的平台，但也想自己做**

查證後確認第 1 點屬實。`products` 表有 11 個欄位，但商品編輯器**只能改 3 個**：

| 欄位 | 用途 | 目前能不能改 |
|---|---|---|
| `name` | 手串名稱 | ✅ |
| `price_cents` | 售價 | ✅ |
| `status` | 上架狀態 | ✅ |
| `description` | 商品故事／設計理念 | ❌ **碰不到** |
| `wrist_size_cm` | 手圍 | ❌ **碰不到** |
| `manual_stock` | 手動限量（null = 依配方庫存動態算） | ❌ **碰不到** |
| `sort_order` | 排序權重 | ❌ **碰不到** |
| `slug` | 網址代稱 | ❌ 建立後無法修改 |

也就是說，商品有故事可寫、有手圍可標、可以限量、可以排序——但店主**一個都填不了**。
前台就算做好也沒東西可顯示。

## 決策

### 1. 自建前台，第一版範圍由店主定案

店主明確指定：

> 「可以快速付款下單，成功後可以讓他自己選擇要不要加入會員，
> 一律使用 GOOGLE 登入，下單成功後必須把訂單資料 EMAIL 給客戶」

拆解成四條規則：

| 規則 | 設計含意 |
|---|---|
| **快速下單** | 結帳**不強迫註冊**。填姓名、電話、地址、Email 就能送出 |
| **事後才問會員** | 會員邀請出現在**下單成功頁**，不是結帳流程中——不擋轉換 |
| **只用 Google 登入** | **不自建密碼**。沒有密碼就沒有密碼外洩、沒有忘記密碼流程 |
| **訂單確認信** | 下單成功自動寄給客戶，內含訂單編號、明細、匯款帳號 |

### 2. FreeStore 先並行，自建穩定後再收

不立刻關閉 FreeStore。自建前台上線後實際跑一陣子，確認沒問題再收掉。
代價是中間期間商品要兩邊各維護一份。

### 3. 後台上架功能補完，且**優先於**前台

前台顯示什麼，取決於後台填得了什麼。順序不能顛倒。

## 為什麼這次不算「推翻決策」

ADR-0008 的核心判斷是「先驗證有沒有人買，不要為了系統好看而延後開賣」。
這個判斷至今成立，所以本 ADR **不關閉 FreeStore**，只是增加一條自己的路。

當時也刻意保留了自建所需的資產（ADR-0008 原文：「暫時用不到但留著不刪，
日後若要自建前台可直接用」）：

- `src/contracts/order.ts` 的 `cartSchema`、`CART_COOKIE_NAME`、`checkoutSchema` **都還在**
- `orders` / `order_items` 本來就是為自建前台設計的，含 `customer_email`
- `docs/05-DESIGN-SYSTEM.md` 的前台規範保留著

**所以自建前台的購物車與結帳不需要改 schema。** 這是當初決策留下的餘裕。

## 需要的 schema 變更（僅會員功能）

購物車、結帳、訂單都不用改。**只有會員需要新增資料**：

| 變更 | 原因 |
|---|---|
| 新增 `customers` 表 | 存 Google 登入回來的身分（google_sub、email、姓名、頭像） |
| `orders` 增 `customer_id` 欄位（可為 null） | 把訂單掛到會員；null = 訪客下單，仍然合法 |

已登記在 `docs/tasks/BOARD.md` 的「SCHEMA 變更請求」，**尚未執行**。
訪客下單不依賴這兩項，所以第一版可以先上，會員功能隨後補。

## 需要的新套件

| 套件 | 用途 | 替代方案 |
|---|---|---|
| Google OAuth 驗證 | 驗 Google 回傳的 id_token | 手刻 JWT 驗證（不建議，容易出錯） |
| 寄信服務 SDK | 寄訂單確認信 | 見下方說明 |

**Cloudflare Workers 沒有內建 SMTP**，不能用一般寄信方式。可行選項：

| 方案 | 免費額度 | 備註 |
|---|---|---|
| Resend | 3,000 封／月 | API 簡單，Workers 相容 |
| MailChannels | 曾對 Workers 免費，**2024 起改收費** | 已不可行 |
| Cloudflare Email Routing | **只能收信、不能發信** | 不適用 |

已登記在 BOARD 的「套件需求」，**尚未安裝**。

## 後果

**好處**
- 商品資料只維護一份（自建站），不必兩邊同步
- 訂單直接進資料庫，不需要匯出匯入
- 前台能顯示配方透視（FreeStore 做不到）——這是本系統真正的差異化
- 不付 1% 成交費

**代價**
- FreeStore 內建的**電子發票、超商取貨、會員系統**要自己做或放棄
  - 第一版：發票與超商取貨**不做**，維持轉帳 + 宅配
  - 會員只做 Google 登入，不做完整會員中心
- 多了寄信服務這個外部相依（免費額度內，但要申請帳號、設定網域驗證）
- 前台是公開的，多一層安全責任（Cloudflare Access 只保護 `/admin`）

**維持不變**
- 零成本原則：所有選用服務都在免費額度內
- 金流不串接：客戶轉帳，店主人工對帳（同 FreeStore 時期的流程）
- 部署架構不變：Cloudflare Workers + D1 + R2
