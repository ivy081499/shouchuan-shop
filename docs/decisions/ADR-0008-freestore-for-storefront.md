# ADR-0008 前台改用 FreeStore，本系統專注後台

**狀態**：已採用（取代 ADR-0007 的前台部分）
**日期**：2026-09-11

## 背景

店主發現台灣的 FreeStore 免費開店平台（freestore.com.tw），詢問是否還需要自建前台。

查證結果：

| 項目 | FreeStore |
|---|---|
| 費用 | 0 元開店、免月費年費、不綁約，**成交才收約 1%** |
| 轉帳收款 | ✅ 支援，有內建「轉帳通知單」讓客戶回報，商家自行對帳 |
| 金流／物流 | **不強制串接**，三項服務各自獨立開通 |
| 商品庫存 | 有，但只到「這件商品剩幾件」的層級 |
| 公開 API | ❌ 查不到 |

關鍵判斷：FreeStore 能做前台（購物車、下單、轉帳回報），且做得比自建更完整
（含會員、電子發票、超商取貨）。但它**管不到散珠層級**——
它不知道一條手串用了 6 顆草莓晶，也算不出「還要跟哪家店叫多少貨」。

而店主目前**零客戶**，最該先驗證的是「有沒有人買」，不是「系統好不好」。

## 決策

**採方案 C：前台用 FreeStore 先開賣，後台自建。**

- ❌ 取消 S1（設計系統／前台外殼）與 S2（前台頁面）兩個工作流
- ✅ 後台（S3 珠子與配方、S4 訂單、S5 報表與匯入）照原計畫做
- ➕ 新增：**FreeStore 訂單匯入**功能，取代原本「前台直接寫入資料庫」的路徑

## 後果

**好處**
- 今天就能開始賣東西，不必等系統做完
- 1% 成交費在沒有營收前是 0 元，符合零成本原則
- 開發範圍砍半，後台能更快完成
- 已完成的 schema、contracts、資料層**全部保留可用**（見下）

**代價**
- FreeStore 沒有公開 API → 訂單資料要靠**匯出檔匯入**後台，無法即時同步
- 商品資料要在兩邊各維護一份（FreeStore 上架、後台建配方）
- 綁在 FreeStore 上，日後要搬遷有成本
- 若 FreeStore 後台沒有匯出功能，就只能手動輸入訂單（待店主確認）

## 為什麼既有工作沒有白費

`db/schema.ts` 的 `orders` / `order_items` 原本就設計成存「訂單編號、金額、狀態、成本快照」，
FreeStore 的訂單塞得進去，**不需要改 schema**。這正是凍結 schema 前先想清楚資料模型的價值。

保留且仍然有用的：
- schema 全部 11 張表
- `src/lib/`（金額、成本、規格解析）—— 這是系統核心價值
- `src/data/`（訂單、珠子、商品、報表資料層）
- `src/contracts/` 大部分；購物車相關型別（`cartSchema`、`CART_COOKIE_NAME`、`checkoutSchema`）
  暫時用不到但留著不刪，日後若要自建前台可直接用

`docs/05-DESIGN-SYSTEM.md` 保留——後台仍需視覺規範，
只是不必為前台做展示型設計（配方透視 signature 元素暫時擱置）。

## 待確認

FreeStore 後台的訂單頁是否有「匯出 CSV／Excel」功能。
- 有 → 做匯入解析器，流程同淘寶匯入（上傳→解析→逐列確認→寫入）
- 沒有 → 後台需提供手動建立訂單的介面
