# ADR-0006 匯入必須人工逐列確認

**狀態**：已採用
**日期**：2026-09-11

## 背景

淘寶 `订单数据.xlsx` 的「型號款式」欄由賣家自由填寫，格式極不一致。
用實際樣本測試解析器，發現三類情況：

| 類型 | 範例 | 能否自動判讀 |
|---|---|---|
| 明確顆數 | `约6mm*5颗`、`6mm/10颗`、`5颗装`、`3.5mm/颗` | ✅ |
| 賣家自稱約數 | `【约60颗左右】` | ⚠️ 實收可能不同 |
| 無顆數資訊 | `24款`、`56亮天蓝` | ❌ |
| 非珠子 | `长约45米粗约0.8mm`（彈力線） | ❌ 按米計 |

顆數錯 → 單顆成本錯 → 毛利與採購報表全錯。這是會直接影響店主生意判斷的數字。

## 決策

解析器輸出**建議值**，附信心等級（`parsed` / `estimated` / `manual`），
匯入流程強制為：

```
上傳 → 解析 → 逐列顯示（顆數、信心等級、算出的單顆成本）
     → 店主確認／修改 → 按下確認 → 才寫入資料庫
```

`beadsPerUnit` 為 null 的列**不得**通過確認。

## 後果

**好處**
- 錯誤數字不會靜默進入系統
- 店主對自己的成本數字有信心

**代價**
- 匯入不是一鍵完成，筆數多時要花時間確認

**這是店主明確要求的規矩**（他的原話：抄資料不准憑記憶、超過 5 筆要先列出來看過）。
任何工作流都不得為了流暢度略過確認步驟。

---

## 修訂 2026-09-14：解析不出時預設 1 顆，確認移至試算表

**狀態**：已採用，取代上方「`beadsPerUnit` 為 null 的列不得通過確認」

### 變更

解析器 `parseBeadSpec()` 判讀不出顆數時，不再回傳 null，一律回傳 `beadsPerUnit: 1`，
`confidence` 仍為 `manual`。匯入流程不再因為 null 而卡住。

### 為什麼改

店主的實際工作流是：**先在雲端試算表逐列確認顆數，確認完的資料才交給系統匯入。**
人工逐列確認這一關仍然存在，只是地點從網頁的確認畫面移到了試算表。

原本的 null 設計假設確認發生在網頁上，與實際工作流不符：
51 列裡有 28 列解析不出，全部卡住，等於整批無法匯入。

### 代價（店主已知悉並同意）

填 1 會讓未經確認的單顆成本**高估到最多 10 倍**。以 2026-09-10 那批為例：

| 商品 | 件數 | 填 1 的單顆成本 | 若實際每件 10 顆 |
|---|---|---|---|
| 沙金桶珠 24款 | 4 | ¥5.35 | ¥0.54 |
| 沙金轉運珠 06款 | 6 | ¥3.79 | ¥0.38 |
| 彈力線 45 米 | 1 | ¥5.47／「顆」 | 按米計，根本不是顆 |

錯誤成本會流進毛利與採購報表。**防線是試算表那一關**——
交給系統的資料必須是店主已在試算表確認過顆數的版本。

`confidence` 保持 `manual`，是留給日後查核用的線索：
這列的 1 是預設值還是店主確認的結果，靠 `manual` 標記無法區分，
若要區分需另外設計欄位（本次未做）。


## 雲端試算表的分頁命名（2026-09-14 定案）

店主每次交付**一份** Excel，內容可能橫跨多天訂單，因此分頁名不綁訂單日期，
改用**批次號**，並以前綴區分資料來源：

| 分頁 | 內容 | 誰維護 |
|---|---|---|
| `原始-01` | 店主給的淘寶匯出原文 | 店主，程式不得改動 |
| `解析-01` | 解析器輸出的顆數確認表 | Claude 產生，店主確認顆數 |

- 編號成對：`原始-02` 配 `解析-02`，依交付順序遞增。
- 前綴直接說明誰是誰，一眼分辨原始資料與解析結果。
- 訂單日期範圍寫在解析分頁裡，不進分頁名（一批可能跨多天）。

`解析-NN` 的欄位順序對齊 `/admin/import` 確認畫面，方便逐格照抄：

列號、商品（淘寶原文）、規格、金額、件數、**每件顆數**、總顆數、狀態、
單顆成本、珠子名稱（繁體）、淘寶連結、略過

- 「總顆數」為公式 `=IF(每件顆數="","",件數×每件顆數)`，店主改顆數會自動重算。
- 「狀態」顯示 `已解析` / `約數` / `要填`；**`要填` 代表顆數是預設值 1，尚未確認**。
