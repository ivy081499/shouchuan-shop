# 前台自建與上架補完 — 實作計畫

**決策依據**：`docs/decisions/ADR-0012`
**建立日期**：2026-09-22
**狀態**：規劃完成，**尚未開始實作**

---

## 一句話目標

讓店主能在後台完整上架一條手串，客人能在自己的網站上看到它、買下它，
下單後收到確認信，並可自由選擇要不要用 Google 註冊成會員。

---

## 為什麼要分四個階段

每個階段結束都能**單獨驗收、單獨上線**，不必等全部做完才看得到東西。
順序不可調換，理由寫在各階段。

| 階段 | 做什麼 | 結束時可以驗收什麼 | 需要 schema？ |
|---|---|---|---|
| **A** ✅ **已完成** | 後台上架補完 | 一條手串的所有欄位都填得了 | 否 |
| **B** ✅ **已完成** | 前台看商品 | 客人看得到商品頁（還不能買） | 否 |
| **C** ✅ **已完成** | 購物車與結帳 | 客人買得到、你收得到訂單與信 | 否 |
| **D** | 會員（Google 登入） | 客人可註冊、查自己的訂單 | **是** |

**A 必須最先做**：前台顯示什麼取決於後台填得了什麼。沒有商品故事、沒有手圍，
前台做出來也是空的。

**D 放最後**：會員是「加分」不是「必要」。訪客下單（C）自己就能成立，
會員晚一週上線不影響開賣。而且 D 要改 schema，隔離開來比較安全。

## 階段 C：購物車與結帳（第一版核心）✅ 已完成（2026-09-24）

**目標**：客人買得到，你收得到訂單與 Email。

**完成狀況**：C-1～C-5 全部做完，**未改 schema、未產生 migration、未裝任何套件**。

實測（在隔離的 worktree 資料庫副本上跑，測完已清乾淨）：
加入購物車 → 超量被擋（「最多只能買 1 條」）→ 購物車改量／移除 →
結帳（手機號碼格式驗證有擋）→ 訂單成立 `SC-260924-99LM` →
回報末五碼（狀態轉「待確認」）→ 呼叫 `confirmPaymentAndDeductStock()` →
**6 種珠子庫存正確扣減、stock_ledger 留下 6 筆稽核紀錄**。
成本快照 `unit_cost_cents` = 20214（NT$202.14），與配方材料成本相符。
下單當下 `stock_deducted=0`、`paid_at=null`，**確認收款前庫存完全沒動**。
375px 下 `/`、`/cart`、`/checkout`、`/order/[orderNo]` 四頁都不橫向捲動。

### C-1 購物車

- 型別 `cartSchema`、`CART_COOKIE_NAME` **已存在可用**
- 存在 cookie，不需要登入
- 加入、移除、改數量
- **即時檢查可售數量**，超過就擋下

### C-2 結帳頁

**不強迫註冊**。表單欄位：姓名、電話、Email、收件地址、備註。
`checkoutSchema` **已存在可用**。

送出後：

1. 再次檢查庫存（避免同時有人下單）
2. 建立 `orders`（狀態 `pending_payment`）與 `order_items`
3. **寫入成本快照** `unit_cost_cents` —— 這是日後查毛利的依據，不可省略
4. 清空購物車 cookie
5. 寄訂單確認信
6. 轉到成功頁

**此時不扣庫存。** 扣庫存在店主確認收款時發生（`confirmPaymentAndDeductStock()`），
這個不變量不能破壞。

### C-3 訂單確認信

寄給客戶，內容：

- 訂單編號
- 買了什麼、幾條、多少錢
- **匯款帳號**（從 `settings` 表讀，不要寫死）
- 提醒：匯款後請回報末五碼

**技術限制**：Cloudflare Workers 沒有 SMTP，要用 HTTP API 寄信（見 ADR-0012）。
寄信失敗**不可以讓下單失敗**——訂單要先存好，寄信失敗只記錄，店主仍看得到訂單。

### C-3 實作結果：沒有裝套件

`src/app/(store)/email.ts`，直接 `fetch` 打 Resend 的 API。
BOARD 原本登記要裝寄信 SDK，實際做下去發現**不需要**：Resend 的寄信就是一個 POST，
手寫六行就完了，裝 SDK 只是多一個相依。同 B-4 圖片壓縮的結論。

**⚠️ 店主要做兩件事，信才會真的寄出去：**

1. 申請 Resend 帳號並驗證寄件網域
2. 設定兩個環境變數：`RESEND_API_KEY`、`MAIL_FROM`

**兩個變數沒設定之前，下單完全正常，只是不寄信**（不會報錯、不會擋流程）。
設好之後不必改任何程式，信自動開始寄。

另有選用的 `SITE_URL`，用來組信裡的訂單連結；沒設就從請求標頭推，本機開發不必設。

```

  id, google_sub（Google 的使用者唯一 id）, email,
  name, picture_url, created_at, updated_at
```

### D-2 Google 登入

- 一律 Google，**不自建密碼**（沒有密碼就沒有密碼外洩風險）
- 流程：Google 授權 → 驗證 id_token → 找或建 `customers` → 發 session cookie
- Session 用 HttpOnly + Secure cookie

### D-3 訂單歸戶

註冊當下，把**同一個 Email 的既有訂單**掛到這個會員身上，
客人一登入就看得到過去的訂單，不必客服處理。

### D-4 會員頁 `/me`

- 我的訂單列表與狀態
- 結帳時自動帶入上次的收件資料

**驗收**：用 Google 註冊，看得到剛才訪客身分下的那筆訂單。

## 明確不做（第一版）

| 項目 | 原因 |
|---|---|
| 電子發票 | 要串財政部，流程長。先用手開或不開 |
| 超商取貨 | 要跟物流商簽約。先只做宅配 |
| 刷卡金流 | 要商店審核、有手續費。維持轉帳 |
| 密碼註冊 | 只用 Google，避免密碼安全責任 |
| 優惠券／促銷 | 還沒有客戶，先不做 |
| 商品評價 | 同上 |

這些不是「不好」，是**現在做了也沒用**。有客戶之後再依實際需求加。

## 風險與對策

| 風險 | 對策 |
|---|---|
| **超賣**：兩人同時買最後一條 | 結帳時重新檢查可售量；確認收款扣庫存時再檢查一次（`confirmPaymentAndDeductStock` 已有防呆） |
| **寄信失敗導致下單失敗** | 訂單先寫入資料庫，寄信失敗只記錄不擋流程 |
| **前台是公開的** | Cloudflare Access 只保護 `/admin`；前台所有寫入都要驗證輸入（zod 已有 schema） |
| **免費額度爆掉** | 圖片走 R2 直出、列表頁避免 N+1 查詢（`docs/03-ARCHITECTURE.md` 守則） |
| **FreeStore 並行期商品不同步** | 以自建站為主，FreeStore 只保留既有商品不再新增 |
| **改 schema 污染 D1** | 階段 D 另開 schema session，且不與其他工作流同時進行 |
