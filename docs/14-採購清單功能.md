# 採購清單功能規格

店主主動挑貨的採購清單。與現有「採購需求表」互補，不取代。

> ✅ **已實作（2026-10-26）。** 店主指示直接做完，schema 已建表、migration 0005 已套用。
> 頁面：`/admin/reports/purchase-list`

---

## 1. 為什麼需要這個功能

現有 `/admin/reports/purchasing`（採購需求表）是**訂單驅動**的：
展開未出貨訂單的配方，扣掉庫存，算出缺口。

**在零客戶階段它永遠是空的。** 店主現在的真實需求是另一件事：

| | 現有採購需求表 | 本功能 |
|---|---|---|
| 觸發 | 客戶下單 | 店主主動想補貨 |
| 算法 | 訂單需求 − 庫存 | 店主自己決定要補什麼、補多少 |
| 零客戶時 | 空白 | 可正常使用 |
| 狀態 | 即時計算，不留存 | **存檔，可跨 session 續用** |

兩者並存，不互相取代。採購需求表回答「訂單要我叫什麼」，
本功能回答「我想補什麼」。

---

## 2. 使用情境

2026-10-26 盤點：現有 72 種、683 顆，但貴珠分散在 17 種、
其中 10 種僅 3–5 顆（各只能做 1 條甚至 0 條）。
擺攤目標 30 條，實際只能做約 19 條。

店主要做的事是：**挑出要補深的那幾種，照店家分組下單。**
這需要勾選、調整數量、存檔、下次打開繼續，以及一份能照著買的清單。

## 3. Schema 變更請求

### 新增 `purchase_lists` 表

```
purchase_lists
  id            INTEGER PK AUTOINCREMENT
  name          TEXT NOT NULL              -- 清單名稱，例「2026-11 擺攤補貨」
  note          TEXT                       -- 備註
  status        TEXT NOT NULL DEFAULT 'draft'
                  -- draft=編輯中 / ordered=已下單 / closed=已結案
  created_at    INTEGER NOT NULL
  updated_at    INTEGER NOT NULL
```

### 新增 `purchase_list_items` 表

```
purchase_list_items
  id              INTEGER PK AUTOINCREMENT
  list_id         INTEGER NOT NULL  → purchase_lists.id  ON DELETE CASCADE
  bead_id         INTEGER NOT NULL  → beads.id
  qty             INTEGER NOT NULL DEFAULT 0    -- 要叫的顆數
  source          TEXT NOT NULL DEFAULT 'manual'
                    -- manual=手動勾選 / shortage=從缺貨一鍵帶入
  note            TEXT
  created_at      INTEGER NOT NULL
  updated_at      INTEGER NOT NULL

  UNIQUE (list_id, bead_id)   -- 同一清單同一顆珠只能一列
```

**設計理由**

| 決定 | 為什麼 |
|---|---|
| 兩張表而非一張 | 清單要能命名、存多份（這次補貨／下次補貨），不是單一全域狀態 |
| `qty` 存在 item 而非算出來 | 店主會手改數量，不能每次重算覆蓋 |
| `source` 欄位 | 要能分辨哪幾列是一鍵帶入的、哪幾列是自己加的，供 UI 標示 |
| `UNIQUE(list_id, bead_id)` | 一鍵帶入時用 upsert，避免重複列 |
| 不存單價與金額 | 單價會變，一律即時從 `beads.unit_cost_cents` 讀，不做快照 |
| `status` 三態 | 下單後要能標記，否則分不清哪張清單已經買了 |

**不做的事**

- 不新增 `beads` 欄位（schema 凍結，且勾選狀態不屬於珠子本身）
- 不把資料塞進 `beads.note`（CLAUDE.md 明文禁止繞道）
- 不存金額快照（成本公式一律呼叫 `src/lib/costing.ts`）

## 4. 畫面規格

路徑：`/admin/reports/purchase-list`（屬 S5 工作流可寫路徑）

### 4.1 清單選擇列

頁面最上方。

```
清單：[2026-11 擺攤補貨 ▾]  [＋ 新建清單]  [標記已下單]
```

### 4.2 一鍵帶入缺貨

清單選擇列下方，一個按鈕：

```
[ 一鍵帶入缺貨品項 ]   低於安全庫存的 N 項
```

**行為**

1. 取所有 `is_archived = 0` 且 `stock_qty < reorder_point` 的珠子
2. 建議數量 = `reorder_point × 2 − stock_qty`（補到安全庫存的兩倍）
3. 以 `source = 'shortage'` upsert 進當前清單
4. 已存在的列**只更新 qty**，不覆蓋店主手改的 note
5. 完成後顯示「帶入 N 項」，並把這幾列在表格中標示

> 建議數量用「安全庫存 × 2」而非「補到安全庫存」。
> 剛好補到安全庫存的話，做幾條就又低於門檻，等於每個月都要下單。

### 4.3 主表格

全部珠子一列一行，可勾選。

| 欄 | 內容 | 排序 | 篩選 |
|---|---|---|---|
| ☑ | 勾選框 | — | 只看已勾選 |
| 珠名 | `beads.name` | ✓ 中文筆畫 | 關鍵字搜尋 |
| 分類 | 水晶／玉石／配件／線材 | ✓ | ✓ 多選 |
| 尺寸 | `size_mm` | ✓ 數值 | ✓ 區間 |
| 現有庫存 | `stock_qty` | ✓ 數值 | ✓ 只看低於安全庫存 |
| 安全庫存 | `reorder_point` | ✓ 數值 | — |
| 單顆成本 | `unit_cost_cents` | ✓ 數值 | ✓ 價格級別 |
| **要叫數量** | 可編輯數字輸入框 | ✓ 數值 | ✓ 只看有填數量 |
| 小計 | `qty × unit_cost_cents` | ✓ 數值 | — |
| 店家 | `suppliers.name` | ✓ | ✓ 多選 |
| 淘寶規格 | `source_spec` | — | — |
| 連結 | `source_url` → 「去買」 | — | ✓ 只看有連結 |

**互動規則**

- 勾選框與數量欄連動：填了數量自動勾選；取消勾選數量歸零並從清單刪除
- 數量輸入採 debounce 500ms 後存檔，不要每個按鍵都打 API
- 帶入的列（`source = 'shortage'`）在珠名旁加小標記，區別於手動勾選
- 庫存低於安全庫存的列，庫存數字用警示色（沿用 `Td` 的 `alert` 屬性）

### 4.4 統計列

表格上方，沿用 `Stat` 元件：

| 指標 | 內容 |
|---|---|
| 已選品項 | 清單內列數 |
| 總顆數 | `SUM(qty)` |
| 預估花費 | `SUM(qty × unit_cost_cents)`，用 `Money` 元件 |

### 4.5 產生下單清單

頁面底部按鈕：`[ 產生下單清單 ]`

輸出**依店家分組**的純文字區塊，可一鍵複製：

```
───── 八祥梦旗舰店 ─────
和田玉 6mm 奶白     20 顆    https://item.taobao.com/...
黃塔晶 8mm          20 顆    https://item.taobao.com/...
小計 約 NT$1,200

───── 其他店鋪 ─────
...

總計 約 NT$2,450
```

依店家分組的理由同現有採購需求表：淘寶要一家一家下單，
跨店分開才能照著買。

## 5. API 規格

路徑：`src/app/api/admin/reports/purchase-list/**`（S5 可寫）

| 方法 | 路徑 | 用途 |
|---|---|---|
| GET | `/` | 取清單列表 |
| POST | `/` | 新建清單 |
| GET | `/[id]` | 取單一清單含所有 items 與珠子資訊 |
| PATCH | `/[id]` | 改清單名稱、備註、status |
| DELETE | `/[id]` | 刪清單（items 隨 CASCADE 刪除） |
| PUT | `/[id]/items/[beadId]` | upsert 單列（改數量） |
| DELETE | `/[id]/items/[beadId]` | 刪單列（取消勾選） |
| POST | `/[id]/fill-shortages` | 一鍵帶入缺貨 |

**不變量**

- `qty <= 0` 的列視為未選，API 收到時直接刪除該列，不留 0 的列
- `fill-shortages` 必須是 upsert，重複按不產生重複列
- 金額一律整數新台幣分，用 `src/lib/money.ts`

## 6. 與既有功能的關係

| 既有 | 關係 |
|---|---|
| `/admin/reports/purchasing`（採購需求表） | **不修改。** `src/data/reports.ts` 是凍結檔 |
| `beads` 表 | 只讀，不寫 |
| `suppliers` 表 | 只讀，用於分組 |
| `src/lib/costing.ts` | 金額計算一律呼叫它，不自己寫公式 |
| 進貨匯入流程 | 無關。本功能產出「要買什麼」，匯入處理「買回來了」 |

**資料層新檔**：`src/data/purchase-lists.ts`
不要寫進凍結的 `src/data/reports.ts`。

## 9. 實作後的落差記錄

### 安全庫存全是 0

實作時發現 **72 種珠子的 `reorder_point` 全部是 0**，
原規格的「低於安全庫存就帶入」判斷會讓按鈕永遠帶入 0 項。

**處理**：`fillShortages()` 改為兩段判斷，依序採用——

| 順位 | 條件 | 建議數量 |
|---|---|---|
| 1 | 有設安全庫存且低於門檻 | 安全庫存 × 2 − 現有庫存 |
| 2 | 完全沒設安全庫存時的備援 | 補到 20 顆 |

備援的門檻是「主石不足 8 顆」（單顆成本 ≥ NT$10 視為主石）。
依 `test` 配方一條約用 4 顆主石，不足 8 顆連兩條都做不出來。
目前這條規則抓到 44 項。

介面會說明當下用的是哪一種判斷，不讓店主誤以為是安全庫存設定生效了。

**後續**：店主在珠子頁設好 `reorder_point` 後，自動切回第 1 種判斷，程式不必改。

### 排序在記憶體做

`qty` 與 `subtotal` 來自 left join 後的計算欄，SQL 排序寫起來繞。
珠子總數是數十到數百筆，記憶體排序成本可忽略。

### 排序與篩選寫在網址

不做純客戶端篩選，條件一律進 query string。
好處是重新整理不會掉條件，也能把特定檢視加入書籤。
