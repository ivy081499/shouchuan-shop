# 業務規則

這份文件是所有實作的依據。**程式行為與此文件衝突時，以此文件為準**；覺得文件本身有問題，先問店主，不要自行改程式。

---

## 1. 生意長什麼樣子

店主向淘寶多家店鋪購入**散珠**（一顆一顆的珠子），自行設計、手工編成**手串**（手鍊）販售。

- 目前**零客戶**，屬於初期試營運，一切以最低成本為原則。
- 單人經營，出貨、對帳、採購都是店主一個人做。
- 商品是**現成款**：店主先做好或設計好，客戶挑現成的買。**前台沒有客製配珠功能。**

---

## 2. 付款流程（完全不串金流）

這是本系統最關鍵的設計，因為店主不願負擔任何金流費用。

```
客戶下單
   ↓  系統立刻產生「轉帳資訊」：銀行、戶名、帳號、應付金額、專屬訂單編號
客戶自行去 ATM / 網銀轉帳
   ↓  客戶回到網站，填寫「轉帳帳號末五碼 + 轉帳時間」
訂單狀態 → 待確認
   ↓  店主在後台看銀行入帳，核對末五碼與金額
店主按「確認收款」
   ↓  ★ 此刻才實際扣減珠子庫存 ★
訂單狀態 → 已收款
   ↓  店主出貨、填物流單號
訂單狀態 → 已出貨 → 完成
```

**訂單編號**格式：`SC-YYMMDD-XXXX`（XXXX 為亂碼，避免被猜出別人的訂單）。
客戶轉帳時填在備註，店主用它對帳。

### 狀態機（不可自行增減狀態）

| 狀態 | 代碼 | 意義 |
|---|---|---|
| 待付款 | `pending_payment` | 剛下單，還沒轉帳 |
| 待確認 | `payment_reported` | 客戶說他轉了，店主還沒核對 |
| 已收款 | `paid` | 店主確認入帳。**庫存在此刻扣減** |
| 已出貨 | `shipped` | 已寄出，有物流單號 |
| 完成 | `completed` | 結案 |
| 已取消 | `cancelled` | 未付款逾期或客戶取消 |

**不變量**
- `paidAt` 為 null 時**不得**出貨。
- 庫存扣減**只**發生在轉入 `paid` 的那一刻，且由 `stockDeducted` 旗標保證不重複扣。
- 訂單取消時，若已扣庫存則必須加回，並在 `stock_ledger` 留一筆 `order_cancelled`。

## 3. 庫存與超賣（店主已知並接受的取捨）

店主要求：**付款確認才實扣庫存**（不要下單就預扣）。

代價：兩位客戶同時下單同一款、而材料只夠做一條時，兩張訂單都會成立。

**處理方式**（店主已同意）：
- 下單時**不扣庫存**，但把「下單當下的可售數量」記在 `order_items.availableAtOrderTime`。
- 後台訂單列表自動計算目前庫存是否仍足夠，不足者**標紅警示**。
- 由店主決定要補料、還是聯繫客戶退款。

不要自作主張改成預扣或加排程釋放，那是另一個方案，需店主重新決定。

## 4. 成本計算

### 資料來源
店主從淘寶下載的 `订单数据.xlsx`（進貨明細）。欄位：
訂單號、訂單提交時間、訂單狀態、**店鋪名稱**、商品名稱、商品連結、**型號款式**、商品數量、**商品金額**、實付金額、運費、物流公司、物流單號。

### 公式（唯一實作：`src/lib/costing.ts`）

```
單顆成本(TWD分) = (商品金額 × 件數 + 攤得運費) × 匯率 ÷ (件數 × 每件顆數)
```

- 金額一律**整數新台幣分**，禁止浮點數。
- 匯率存「放大 100 倍的整數」（4.5 → 450），**凍結於該筆進貨**，日後匯率變動不追溯。
- 運費依各品項金額比例攤提，**餘數給最後一項**，保證加總等於總運費。

已用真實資料驗證（匯率 4.5）：

| 品項 | 每顆 |
|---|---|
| 8A白水晶 6mm 约60颗 × 2件 | NT$2.01 |
| 蜜桃粉玛瑙 约4.2mm*3颗 | NT$21.12 |
| 刻面隔片 金色 10顆（含攤運費 ¥1.50） | NT$2.06 |
| S925銀珠 2.5mm 單顆 × 8件 | NT$4.64 |

### ⚠️ 顆數解析必須人工確認

淘寶「型號款式」欄由賣家自由填寫，格式極不一致。解析器（`src/lib/bead-spec.ts`）分三種信心等級：

| 等級 | 意義 | 範例 |
|---|---|---|
| `parsed` | 有把握 | `约6mm*5颗`、`6mm/10颗`、`5颗装`、`3.5mm/颗` |
| `estimated` | 賣家自己說是約數 | `【约60颗左右】` — 實收可能不同，需實際數過 |
| `manual` | 完全解析不出 | `24款`、`56亮天蓝`、`长约45米`（線材按米計） |

**匯入流程強制為**：
```
上傳 xlsx → 解析 → 表格逐列顯示（顆數、信心等級、算出的單顆成本）
          → 店主逐列確認／修改 → 按確認 → 才寫入資料庫
```

**任何工作流都不得略過確認步驟自動寫入。** 這是店主明確要求的規矩。

## 5. 商品與配方

- **手串（product）**＝前台販售單位，有售價、圖片、手圍。
- **配方（recipe）**＝這條手串用了哪些珠、各幾顆。這就是店主要的「勾選使用哪些珠」。
- 手串材料成本 = Σ(每顆珠成本 × 用量)，自動算出，店主不必手動維護。
- **可售數量**預設由配方與庫存動態算出（木桶效應：取各珠「庫存÷用量」的最小值）；也可在 `manualStock` 手動限量。

## 6. 報表（店主明確要求的三張）

### 6.1 採購需求表（最重要）
> 「依目前客戶下單的手串，我應該要有多少珠、還要叫多少貨、店家是誰」

```
應備顆數 = Σ(未出貨訂單中每條手串的配方用量 × 該手串數量)
待採購   = 應備顆數 + 安全庫存 − 現有庫存   （最小為 0）
```

**必須依「店鋪（supplier）」分組**，每列附該珠的淘寶連結，讓店主可以照著一家一家下單。

「未出貨訂單」＝狀態為 `payment_reported`、`paid` 的訂單（已收款未出貨 + 待確認）。
是否納入 `pending_payment`（還沒轉帳的）由店主在報表上切換，預設**不納入**。

### 6.2 毛利表
每個商品／每張訂單的售價、成本、毛利、毛利率。
成本用**訂單當下的快照**（`order_items.unitCostCents`），不隨日後珠價變動。

### 6.3 庫存表
每顆珠的現有庫存、低於安全庫存的示警、以及「還能做幾條某手串」。

---

## 7. 店主的日常操作

1. 早上看後台首頁：有沒有待確認的轉帳、有沒有超賣警示
2. 核對銀行入帳 → 按「確認收款」
3. 出貨 → 填物流單號
4. 每週看採購需求表 → 照著去淘寶下單
5. 收到貨 → 上傳 xlsx → 逐列確認顆數 → 寫入庫存

系統要讓這五件事都很快完成，這是後台的設計目標。
